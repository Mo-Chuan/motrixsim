# Technical README

让目标读者迅速理解项目定位、核心技术能力与实验结果，并能进入演示、示例和首次运行流程。README 采用技术报告的表达方式，正文围绕项目能力与使用路径组织，不套用论文结构。

## 表达原则

1. **直接陈述技术事实。** 用明确的对象、方法、机制和结果说明：处理什么问题、采用什么技术、得到什么结果。以信息密度替代修辞——用具体模型、规模、参数和指标，不用形容词、口号、反问和劝说。
2. **按问题—方法—结果推进。** 场景需求、技术方案与可观察效果自然成段，不机械加小标题；用正面陈述界定能力与适用范围，不用"并非……""不只是……"等否定式组织正文。
3. **结论与证据对应。** 能力由实现和示例支撑，定量结论由测量支撑并注明条件（设备、规模、配置）；条件放在帮助读者解释结论的位置，完整设置进文档或补充材料。
4. **每个主题只解释一次。** Feature 本身回答选择理由，不另设"为什么选择"重复叙述。
5. **以读者任务筛选信息。** 每句话应帮助读者理解技术、判断结果或完成操作；删除后不损失这三类信息的句子直接删除。素材制作过程、预览时长、编码参数、写作安排和显而易见的点击提示属于编辑信息，放维护记录，不进 README。
6. **沿用用户已确认的方向。** 保留定位措辞、Feature 顺序、语言与展示偏好；局部修改不动其他既有内容。

详细示例见 [叙事与 Feature 选择](references/narrative-and-features.md)。

## 工作流程

### 1. 理解材料

读取当前 README、仓库指引及相关发布配置；按需阅读技术报告、示例、实验记录和媒体说明。在内部整理证据映射：Feature → 实现依据 → 代表场景 → 媒体或数据 → 示例入口。只为本次修改搜集材料，不遍历仓库。项目事实与阶段性决策以仓库材料为准，Skill 只维护通用方法。

### 2. 确定主张与顺序

提炼一句项目定位，筛选用户价值明确、有技术辨识度、有证据支撑的 Feature，按技术链路排序。用户要求评审时给出判断和建议；要求修改时直接形成可阅读版本。关键事实缺失时先完成可确定部分。

### 3. 组织内容与展示

推荐阅读路径：定位与资源入口 → 纵向目录 → 核心 Feature → 快速开始 → 示例与生态 → 平台、社区、许可、引用。目录用纵向 Markdown 列表；文档、在线体验等少量入口可横排；首屏避免长篇行业背景。

- Feature 默认纵向小节：标题 → 一段精简描述（1–3 句，含关键机制）→ 媒体 → 深入入口。图像已表达的动作不在正文复述；详细原理与次要实验通过链接提供。
- 表格用于比较、平台矩阵或示例索引；只有同构内容适合逐行浏览时才用 Feature Table。
- 布局细节与素材处理见 [排版与媒体](references/layout-and-media.md)。

### 4. 建立首次运行路径

区分两类读者：运行项目自带示例需要完整环境（克隆仓库、拉取资源、同步依赖）；在已有项目中集成只需安装包和一段自包含的最小代码，示例代码不引用仅仓库内存在的资源路径。两条路径各自独立走通。

每条路径包含前置条件、工作目录、安装命令、最小运行命令、预期结果与平台差异。平台特例、镜像和完整实验配置放折叠区或独立说明。

### 5. 验证与交付

按改动范围检查（分层验证详见排版与媒体）：删除测试；定位、结论与来源一致；目录锚点与本地链接正确；代码与实际 API 一致；媒体可解码且符合远端约束；Markdown 渲染结构符合预期；diff 聚焦、保留用户已有改动。

验证方法与任务成本相称，交付时如实说明完成的验证范围。提交、推送与发布遵循用户授权范围。
